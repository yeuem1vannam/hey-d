# hey-d: Visualization System

**Date:** 2026-04-17
**Status:** Draft (revised after Plan 1 implementation)
**Approach:** Web Components library + wrapper template + multi-mode rendering (standalone HTML, dev server, cloud), configurable via `.agents/config/visualization/`.

## Revision Log

### 2026-04-17 — Medium revision: rename component tags to `hd-*` prefix

**Trigger:** During Plan 1 execution, `customElements.define()` rejected unprefixed tag names like `card`, `field`, `flow` etc. — the Web Components spec requires a hyphen in custom element names (forward-compat protection against future native HTML elements).

**Resolution:** All 18 component tags renamed to `hd-` prefix (`hd-card`, `hd-field`, `hd-flow`, etc.). Native HTML elements (`<section>`, `<nav>`, `<code>`) remain unprefixed since they're decorated via MutationObserver, not custom-element registration.

**Scope:** Tag names in catalog tables + examples throughout this doc. Semantics and component behavior unchanged.

## Overview

AI-authored visualizations for team alignment. Output of brainstorming/spec flow AND a standalone `hey-d:visualize` skill for ad-hoc mockups.

The existing `hey-d:brainstorming` visual-companion lets the AI drop raw HTML files into a watched directory; the brainstorm-server reloads them in a browser. This works, but every file starts from HTML boilerplate — the AI hand-crafts `<div>`s, CSS classes, and layout over and over.

This system eliminates that boilerplate: a pre-built component library (18 Web Components) lets the AI write declarative markup (`<hd-card>`, `<hd-flow>`, `<hd-ref>`, `<hd-approach>`, etc.) instead of raw HTML. The same content renders in three modes — standalone file, dev server, cloud deployment — without conversion.

**Primary author:** AI. **Primary audience:** humans across teams, for alignment and clarification.

**Scope:** A (UI mockups / wireframes) + C (spec / requirements wireframes) + D (comparisons / tradeoffs). **Out of scope for v1:** B (architecture diagrams), E (state machines beyond linear flows), F (dashboards / charts).

## Architecture

### Core principles

1. **HTML-first, wrapper/content split.** The AI authors HTML fragments (content only). The wrapper (html/head/body/tailwind/components.js) is generated by infrastructure, not by the AI. For cloud, the wrapper is swapped; the content is untouched.
2. **Mount point is `<main>`.** Everything the AI writes lives inside `<main>`. Cloud extraction = `document.querySelector('main').innerHTML`.
3. **Components are Web Components in Light DOM.** Tags are prefixed `hd-*` to satisfy the Web Components spec (which requires a hyphen in custom element names). Parent styles apply; no shadow DOM quirks. Graceful degradation if JS fails.
4. **Tailwind per mode.** CDN Play for dev-server (fast iteration), pre-built bundle for standalone (offline-safe), cloud brings its own build.
5. **Configurable via `.agents/config/visualization/`.** Plugin ships sensible defaults; projects override components, theme, Tailwind config without forking.

### Three-mode architecture

```
               ┌────────────────────────────────┐
  AI writes →  │   content fragment (.html)      │
               │   <main>                        │
               │     <section><hd-card>...</hd-card>   │
               │     <hd-flow>...</hd-flow>            │
               │   </main>                       │
               └────────────────────────────────┘
                             │
         ┌───────────────────┼───────────────────┐
         ▼                   ▼                   ▼
  ┌─────────────┐    ┌─────────────┐    ┌──────────────────┐
  │ Standalone  │    │ Dev server  │    │ Cloud deployment │
  │             │    │             │    │                  │
  │ Inline JS/  │    │ Serve       │    │ Next.js RSC      │
  │ CSS; one    │    │ wrapper +   │    │ reads fragment,  │
  │ file        │    │ reload WS   │    │ wraps in app     │
  └─────────────┘    └─────────────┘    └──────────────────┘
```

The AI never cares which mode. Infrastructure adapts.

## File structure & resolution order

### Plugin ships (defaults)

```
<plugin>/resources/visualization/
  components.js     — Web Components library (the 18 components)
  theme.css         — CSS custom properties + component styles
  tailwind.css      — pre-built Tailwind utilities (pruned to what components use)
  wrapper.html      — HTML template with {{title}} and {{content}} placeholders
  snapshot.js       — Node.js tool: fragment → standalone self-contained HTML
  snapshot.sh       — thin bash wrapper around snapshot.js for convenience
```

### Project overrides (optional, per-project)

```
<project>/.agents/config/visualization/
  components.js     — adds or overrides components (loaded after plugin default)
  theme.css         — overrides CSS variables / component styles (cascade wins)
```

Both files optional. Most projects won't need them. Projects with brand colors or custom components will.

### Wrapper template (served by dev-server / inlined by snapshot)

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8" />
  <title>{{title}}</title>

  <link rel="stylesheet" href="{{tailwind_url}}" />      <!-- plugin's tailwind.css -->
  <link rel="stylesheet" href="{{plugin_theme}}" />      <!-- plugin's theme.css -->
  <link rel="stylesheet" href="{{project_theme}}" />     <!-- optional project override -->

  <script src="{{plugin_components}}"></script>          <!-- plugin's components.js -->
  <script src="{{project_components}}"></script>         <!-- optional project override -->
</head>
<body>
  <main>
    {{content}}
  </main>
</body>
</html>
```

### Resolution order (cascade semantics)

| Resource | Plugin default | Project override | Winner |
|----------|----------------|------------------|--------|
| CSS theme | `theme.css` | `.agents/config/visualization/theme.css` | CSS cascade (last loaded wins per selector) |
| Components JS | `components.js` | `.agents/config/visualization/components.js` | Project's runs after plugin's — can ADD new components (see constraint below) |
| Tailwind | `tailwind.css` | — (not overridable in v1) | Brand colors go through theme.css CSS vars |

### Component override constraint

`customElements.define` throws when a tag name is already registered. This means project overrides can **add new components** but **cannot replace existing ones** by re-registering the same tag name. Two ways a project can customize:

- **Add new components** — register new tag names in `.agents/config/visualization/components.js` (e.g., `<my-custom-card>`). Safe, composable.
- **Restyle existing components** — use `.agents/config/visualization/theme.css` to override the visual rules applied by plugin components. Most "customize the look" needs fit here.

If a project genuinely needs to replace a plugin component's behavior (rare), the workaround is to define a new tag name in their override (`<my-card>`) and update their fragments to use that tag instead of `<hd-card>`. This is a v1 limitation — v2 may add a redefine-friendly loading pattern.

### Why Tailwind isn't user-overridable in v1

Overriding Tailwind would require a rebuild step at snapshot time (read user's `tailwind.config.js` → regenerate `tailwind.css`). Deferred to v2. For v1:

- Users express brand via CSS custom properties in `theme.css` (e.g., `--accent: #0E3B3B;`)
- Components reference those vars (e.g., `hd-card { background: var(--card); }`)
- Stock Tailwind palette + themed CSS vars covers 95% of real-world needs

### Mode-specific resource resolution

| Mode | How resources are served/inlined |
|------|---------------------------------|
| **Dev server** | Brainstorm-server serves plugin defaults from `/resources/`, project overrides from `/.agents/config/visualization/` (same paths, different roots). `onerror="this.remove()"` gracefully handles missing override files. |
| **Standalone snapshot** | `snapshot.js` inlines resolved CSS and JS into the HTML file. Output is one self-contained file with everything embedded — ~150-300KB gzipped. |
| **Cloud** | Cloud app's build step imports `components.js` and `theme.css` from the plugin package; adds project overrides via its own mechanism. Not hey-d's concern beyond the portability contract. |

## Component catalog (v1, 18 components)

Organized into 5 categories. All tags are lowercase, unprefixed, use Light DOM.

### 🏗 Layout (4)

| Tag | Purpose | Key attrs | Slots |
|-----|---------|-----------|-------|
| `<section>` | Top-level page/spec section | `title`, `subtitle`, `id` | default (content) |
| `<hd-card>` | Content container | `title`, `tag` (optional badge text) | default |
| `<nav>` | Top nav bar | `title` | default (nav links) |
| `<hd-tabs>` / `<hd-tab>` | Tab switcher (supports nested sub-tabs) | `<hd-tab>` accepts: `label`, `active`, `badge` | each `<hd-tab>` holds content |

```html
<hd-tabs>
  <hd-tab label="Overview" active>...</hd-tab>
  <hd-tab label="Spec 1" badge="specs">...</hd-tab>
</hd-tabs>
```

### 📝 Content (6)

| Tag | Purpose | Key attrs | Slots |
|-----|---------|-----------|-------|
| `<hd-field>` | Labeled form placeholder | `label`, `size` (sm/md/lg), `type`, `placeholder` | — |
| `<hd-stat>` | KPI / metric display | `label`, `value`, `delta` | — |
| `<hd-tag>` | Label chip | `variant` (default/required/optional/accent/warning) | default (text) |
| `<hd-callout>` | Inline note/translation | `variant` (info/translate/note/warning), `label` | default |
| `<hd-ref>` | Source/reference panel (yellow) | `label` (uppercase badge), `source` (link) | default |
| `<hd-prompt>` | Accent-border prompt row | `label` (e.g. "Q1"), `question` | default (answer placeholder) |

```html
<hd-ref label="REFERENCE — original docx (F)" source="docs/original.md">
  <h4>F-1. Overview</h4>
  <p>Original requirement text...</p>
</hd-ref>

<hd-callout variant="translate" label="EN">
  The client lists their top 5 most fulfilling experiences...
</hd-callout>
```

### 🔀 Flow (4)

| Tag | Purpose | Key attrs | Slots |
|-----|---------|-----------|-------|
| `<hd-steps>` / `<hd-step>` | Numbered step list | `<hd-step>` auto-numbered or takes `num` | each `<hd-step>` holds content |
| `<hd-flow>` / `<hd-flow-item>` | Multi-column with → arrows between | `<hd-flow-item>` takes `label`, `highlight` | each `<hd-flow-item>` holds content |
| `<hd-compare>` | Two-column side-by-side | `label-a`, `label-b` | named slots: `a`, `b` |
| `<hd-matrix>` | 2×2 quadrant matrix | `axis-top` (horiz labels), `axis-left` (vert labels) | named slots: `q1`, `q2`, `q3`, `q4` |

```html
<hd-flow>
  <hd-flow-item label="経験">The actual experience...</hd-flow-item>
  <hd-flow-item label="感情">Emotions it carried</hd-flow-item>
  <hd-flow-item label="価値観">Values revealed</hd-flow-item>
  <hd-flow-item label="教訓" highlight>Lesson learned</hd-flow-item>
  <hd-flow-item label="影響" highlight>How it shapes behavior</hd-flow-item>
</hd-flow>
```

### 🧭 Decision (2)

| Tag | Purpose | Key attrs | Slots |
|-----|---------|-----------|-------|
| `<hd-approach>` | Decision option panel | `title`, `selected` | default (description, pros/cons, etc.) |
| `<hd-tradeoff>` | Pros/cons side-by-side | — | named slots: `pros`, `cons` |

```html
<hd-approach title="Path 2 — matrixdropdown + custom renderer" selected>
  <p>Keep the schema native...</p>
  <hd-tradeoff>
    <ul slot="pros"><li>Reusable</li><li>Fallback-friendly</li></ul>
    <ul slot="cons"><li>One-time infra cost</li></ul>
  </hd-tradeoff>
</hd-approach>
```

### 📄 Document (2)

| Tag | Purpose | Key attrs | Slots |
|-----|---------|-----------|-------|
| `<hd-toc>` | Table of contents | `auto` (generates from `<section>`s), or manual list inside | default (optional manual entries) |
| `<code>` | Syntax-highlighted code block | `language` (e.g. `ts`, `json`, `bash`) | default (code content) |

### Composition over new components

If a pattern doesn't have a component, compose existing ones with Tailwind utilities before asking for a new component. Example: "3-column layout with cards" = `<div class="grid grid-cols-3 gap-4"><hd-card>...</hd-card><hd-card>...</hd-card><hd-card>...</hd-card></div>`.

## Rendering infrastructure (per mode)

### Dev server (existing brainstorm-server, extended)

Current behavior (unchanged): AI writes HTML to `screen_dir`, server watches and serves newest to browser with WebSocket reload.

**Three extensions needed:**

1. **Serve plugin resources** — new routes:
   - `GET /resources/visualization/components.js` → plugin's components
   - `GET /resources/visualization/theme.css` → plugin's theme
   - `GET /resources/visualization/tailwind.css` → pre-built Tailwind (available for parity; not used in dev mode — see below)

2. **Serve project overrides** — new routes:
   - `GET /.agents/config/visualization/components.js` → project file if exists, 404 otherwise
   - `GET /.agents/config/visualization/theme.css` → same

3. **Upgrade the wrapper template** — replace existing `frame-template.html` with the new wrapper. Fragment detection logic unchanged (starts with `<!DOCTYPE` → serve as-is; else wrap in template).

**Tailwind in dev-server:** use CDN Play (`<script src="https://cdn.tailwindcss.com">`) in the wrapper — fast iteration, picks up any utility class the AI writes. Pre-built `tailwind.css` is NOT used in dev mode (only in snapshot).

### Standalone snapshot

**Tool:** `<plugin>/resources/visualization/snapshot.js` (Node.js, cross-platform) with a thin `snapshot.sh` wrapper for convenience.

```bash
hey-d snapshot <fragment.html> [--out <output.html>]
```

**What it does:**

1. Reads the fragment (AI's content; may or may not include `<main>` wrapper)
2. Inlines into a full HTML template:
   - `<style>` containing plugin's `tailwind.css` + plugin's `theme.css` + project's `theme.css` (in order, cascade)
   - `<script>` containing plugin's `components.js` + project's `components.js` (in order, last registration wins)
   - Fragment content inside `<main>`
3. Writes to `--out` path (default: same-dir, `.snapshot.html` suffix)

**Output:** single self-contained file, ~150-300KB gzipped. Email-able, no network needed.

### Cloud portability contract

hey-d does NOT own cloud deployment (infra teams do). We guarantee these contracts so infra can build on top:

1. **`components.js` is a self-contained ES module** (or IIFE if ESM not available). No external imports. Safe to bundle with any build tool.
2. **`theme.css` is vanilla CSS with custom properties.** No preprocessors, no `@import` to remote URLs.
3. **`tailwind.css` is a static build artifact** — cloud teams can regenerate with their own Tailwind config if they want different utility sets.
4. **Content fragments are pure HTML** — no inline `<script>`, no external URL refs. Safe to pass through `dangerouslySetInnerHTML` (React) or equivalent.
5. **Mount point is always `<main>`** — cloud extraction: `document.querySelector('main').innerHTML`.

**Example cloud flow (reference, not shipped as code):**

```tsx
// cloud-app/app/visualize/[slug]/page.tsx
import { auth } from '@/lib/auth';
import { readFile } from 'fs/promises';
import '@hey-d/visualization/components';  // registers Web Components
import '@hey-d/visualization/theme.css';

export default async function VisualizationPage({ params }) {
  const session = await auth();
  if (!session) redirect('/login');

  const fragment = await readFile(`content/${params.slug}.html`, 'utf-8');
  return (
    <main>
      <div dangerouslySetInnerHTML={{ __html: fragment }} />
    </main>
  );
}
```

The cloud team writes this. We make sure the pieces plug in cleanly.

## Skill integration

Three integration points — one shared reference doc, one update to existing skill, one new skill.

### A. Shared reference doc

**New file:** `<plugin>/skills/visualization-components.md`

Single source of truth for the 18 components. Contains:

- Catalog (tag, attrs, slots, visual example per component)
- Composition patterns (e.g., "spec doc = `<section>` containing `<hd-ref>` + `<hd-callout>` + `<hd-card>`s + `<hd-flow>`s")
- Tailwind utility guidance ("use `flex gap-4` before asking for a new component")
- Don'ts ("don't write raw `<div class="fe2-header">`... use `<hd-flow>`")

Both the brainstorming flow and the new `visualize` skill reference this catalog instead of duplicating it.

### B. Update `hey-d:brainstorming` (visual-companion)

**File:** `skills/brainstorming/visual-companion.md`

Changes:

- **Keep:** server-launching flow (brainstorm-server start, per-question-use decision logic, session persistence)
- **Replace:** "how to write the HTML" section — instead of teaching raw HTML, point to `visualization-components.md` for the component API
- **Update:** fragment-vs-document paragraph — clarify that fragments now go inside `<main>` automatically; AI writes component-based markup, never wrapper boilerplate
- **Remove:** any instructions about writing `<html>`/`<head>`/`<body>` manually (the new wrapper handles it)

Estimated change: ~40-60 lines edited, ~30 lines removed, net smaller doc.

### C. New skill: `hey-d:visualize`

**File:** `skills/visualize/SKILL.md`

**Purpose:** ad-hoc visualization outside the brainstorming flow. Lets the user say "show me a mockup of X" or "visualize this architecture" and get a rendered output without going through the full brainstorming → spec → plan workflow.

**Trigger:** user says "visualize [X]", "show me a mockup of [Y]", "wireframe [Z]", "make a spec doc for [W]", etc.

**Skill shape:**

```
1. User request: "visualize [X]"

2. Skill clarifies (one short question):
   - Kind? (mockup / spec doc / comparison / flow)
   - Render target? (dev server for iteration / standalone file / both)

3. AI writes HTML fragment using visualization-components.md as reference

4. Skill produces output per target:
   - Dev server: starts brainstorm-server, writes fragment, tells user the URL
   - Standalone: runs snapshot.sh on the fragment, tells user the output path
   - Both: does the snapshot AND launches dev-server for iteration

5. User iterates or accepts
```

`visualize` is a **direct-action** skill (not a creative-work skill requiring brainstorming first). It produces a visual artifact; it doesn't design a system.

**When to use which:**

| Situation | Use |
|-----------|-----|
| "I have a rough idea and want to explore and design it" | `hey-d:brainstorming` (visualize is part of that flow) |
| "I want to see [specific thing] visualized NOW" | `hey-d:visualize` |
| "I have a finished spec and want to share it with the business team as a standalone file" | `hey-d:visualize` in standalone-snapshot mode |

## Out of scope for v1

| Item | Why deferred |
|------|-------------|
| **B — Architecture / data-flow diagrams** | Needs arrow routing, node positioning — different rendering domain (SVG, graph layout) |
| **E — State machines beyond linear `<hd-flow>`** | Requires branch/merge semantics, graph-based layout |
| **F — Dashboards / charts** | Charting is a distinct dependency (chart.js, d3), own design space |
| **Tailwind config rebuild on override** | Requires build-step infra at snapshot time; CSS-var theming covers 95% of cases for v1 |
| **Cloud deployment implementation** | Infra team's territory; we own the portability contract, not the app |
| **Accessibility audit** | Basic semantic HTML only in v1; formal audit + ARIA pass in phase 2 |
| **Internationalization of component labels** | Component labels are slots, so users can pass any language; no i18n layer in v1 |

## Testing strategy

| Layer | What | Method |
|-------|------|--------|
| **Component rendering** | Each of the 18 components renders correctly in a browser | Gallery page (`examples/gallery.html`) that includes one of each; manual visual check + screenshot regression if tooling allows |
| **Fragment → snapshot** | `snapshot.js` produces a valid standalone HTML with all resources inlined | Shell test: run snapshot on a known-good fragment, grep output for expected inline content, open in browser |
| **Dev-server resource routing** | New routes serve correct files with 404 fallback | Extend existing `tests/brainstorm-server/server.test.js` with new route assertions |
| **Cloud contract** | Components load cleanly in a React app without import errors | Minimal reference integration in `examples/cloud-reference/` — documented, not shipped as app |
| **Skill behavior** | `hey-d:visualize` skill produces a correct artifact | Definitional test (like `test-completion-verifier-agent.sh`) — ask Claude questions about the skill, assert expected answers |

## Migration

**For users of existing brainstorming/visual-companion:**

- Fully backward compatible. Existing flow continues to work.
- Old HTML fragments (raw `<div>` markup) still render — the new wrapper doesn't reject them. They just look ugly without hey-d components.
- Encouragement to migrate: new skill docs reference the component catalog; AI naturally starts using components once catalog is in its context.

**For users with custom `frame-template.html` forks:**

- Breaking change — the template is replaced with the new wrapper.
- Mitigation: keep old template alongside as `frame-template.legacy.html`, document in release notes.
- Users who forked can either migrate to the new wrapper (recommended) or keep using legacy.

**No data migration.** This is pure tooling; no user-generated state is touched.
